# Plugin audit, 2026-09-13

Audit of `pytest_antilru/main.py` against the repository state at commit `29394e2`, run on
Python 3.13.12 with pytest 9.0.3 (the `uv` dev environment in `.venv`).

No security vulnerabilities were found. The plugin does no I/O, evaluates no user input, and reaches
no network. Everything below is a correctness, robustness, or documentation defect.

Every finding was reproduced locally. The repro for each one is included so it can be re-run
without redoing the investigation.

## How the plugin works

Three hooks, all in `pytest_antilru/main.py`:

1. `pytest_load_initial_conftests` (line 24, `tryfirst=True, hookwrapper=True`) saves the real
   `functools.lru_cache` into the module global `old_lru_cache` (line 10), then replaces
   `functools.lru_cache` with a closure, `lru_cache_wrapper`. The patch is installed *before* the
   `yield`, so it is in place before any conftest or test module is imported.
2. `pytest_collection` (line 72) restores `functools.lru_cache = old_lru_cache` after collection
   finishes. So the patch is only live during collection.
3. `pytest_runtest_teardown` (line 79, `tryfirst=True, hookwrapper=True`) calls `cache_clear()` on
   every wrapper recorded in the module-global list `CACHED_FUNCTIONS`, after the `yield`, so it runs
   last among teardown hookwrappers.

`cache_user_function` (line 13) decides whether a newly decorated function is recorded. With an empty
`lru_cache_disabled` ini setting everything is recorded; with a non-empty one, only functions whose
`__module__` string-prefix-matches an entry are recorded.

Two facts that are easy to get wrong and were verified during the audit:

- `functools.cache` **is** covered. Its body looks up the module global `lru_cache` at call time, so
  it resolves to the patched wrapper. Verified: a `@functools.cache` function is busted between tests.
- Both the TOML list form (`lru_cache_disabled = ["a", "b"]`) and the triple-quoted multi-line string
  form shown in `README.md` parse correctly for a pytest `linelist` ini option. The README example is
  valid.

## Findings

Numbered in the order they were originally written, which was by severity at the time. Finding 1
has since been downgraded to Medium during triage, so the list is no longer strictly severity
ordered. Numbers are kept stable because they are referenced elsewhere. Each finding has a
file:line anchor, the evidence, and a suggested direction.

### 1. Medium (was Critical): unpatch leak plus self-recursive wrapper, crashing the next in-process run

Anchors: `pytest_antilru/main.py:10`, `:43`, `:75`.

Two defects compound into one crash.

`old_lru_cache` is a single module-level global (line 10), reassigned on every patch install. It is
not captured in the `lru_cache_wrapper` closure. Meanwhile the restore only happens in
`pytest_collection` (line 75), which many pytest exit paths never reach.

So: a session that exits before collection completes leaves `functools.lru_cache` pointing at
`lru_cache_wrapper` for the remaining life of the interpreter. A *second* pytest session in the same
process then executes line 30-31 and stores the already-installed wrapper into `old_lru_cache`. The
wrapper now calls itself at line 43 (or line 53), forever.

Exit paths measured for whether `functools.lru_cache` is restored:

| Invocation | Restored |
| --- | --- |
| normal run | yes |
| `--collect-only` | yes |
| `--version` | yes |
| no tests found | yes |
| conftest raises on import | **no** |
| usage error (unknown option) | **no** |
| `-h` | **no** |
| `--markers` | **no** |

Blast radius is not theoretical. Any plugin repository that uses the `pytester` fixture hits it,
because `pytester.runpytest()` runs in-process by default, and testing a failing inner run is a
normal thing to do. With `pytest-antilru` installed, one inner run that errors during collection
poisons the next inner run:

```text
INTERNALERROR>   File "pytest_antilru/main.py", line 53, in lru_cache_wrapper
INTERNALERROR>     wrapper = old_lru_cache(**kwargs)
INTERNALERROR>   [Previous line repeated 903 more times]
INTERNALERROR> RecursionError: maximum recursion depth exceeded
```

Repro, in an empty directory with `pytest-antilru` installed:

```python
# conftest.py
pytest_plugins = ["pytester"]
```

```python
# test_pytester.py
def test_inner_collection_error(pytester):
    pytester.makeconftest("raise RuntimeError('boom')")
    pytester.makepyfile("def test_x(): pass")
    result = pytester.runpytest()  # in-process by default
    assert result.ret != 0


def test_inner_normal_run(pytester):
    pytester.makepyfile(
        "from functools import lru_cache\n"
        "@lru_cache\n"
        "def f(): return 1\n"
        "def test_x(): assert f() == 1\n"
    )
    result = pytester.runpytest()
    result.assert_outcomes(passed=1)
```

`pytest -q test_pytester.py` ends in the `INTERNALERROR` above.

Direction: capture the original inside the closure rather than reading a module global at call time,
and refuse to re-patch when `functools.lru_cache` is already the wrapper (detected via an
`_antilru_patched` marker attribute). Leave the `pytest_collection` restore where it is, as
best-effort cleanup. An earlier draft of this section proposed moving the restore to
`pytest_unconfigure`; that was rejected, because changing how long the patch stays installed is
finding 4's design decision and should not be made as a side effect of a crash fix.

Triaged: deferred, not scheduled. Severity downgraded from Critical to Medium, because reaching it
requires two pytest sessions in one interpreter and every current usage (CLI, tox, xdist) forks a
process per session. `tests/` contains no `pytester`, `testdir`, or `runpytest` usage today. See
`docs/future-work-pytester-migration.md` for the adoption plan that makes this live, and for the
regression test to write alongside the fix.

### 2. Low (was High): `AttributeError` on `__module__ is None`, aborting collection

Anchor: `pytest_antilru/main.py:16`.

`cache_user_function` calls `user_function.__module__.startswith(...)` with no guard. A function
compiled into a namespace that has no `__name__` gets `__module__ = None`, and `lru_cache` accepts
any callable, including ones with no `__module__` at all.

Only reachable when `lru_cache_disabled` is non-empty, because the empty-allowlist branch never reads
`__module__`.

Repro:

```ini
# pytest.ini
[pytest]
lru_cache_disabled =
    mymod
```

```python
# mymod.py
import functools

ns = {}
exec('def dyn(x):\n    return x\n', ns)  # no __name__ in globals, so __module__ is None
cached_dyn = functools.lru_cache(maxsize=None)(ns['dyn'])
```

```python
# test_x.py
import mymod


def test_it():
    assert mymod.cached_dyn(1) == 1
```

Result:

```text
pytest_antilru/main.py:16: in cache_user_function
    if user_function.__module__.startswith(module_path):
E   AttributeError: 'NoneType' object has no attribute 'startswith'
```

Collection is interrupted, so the whole run fails rather than one test. Verified with a second,
unrelated test file present: it never runs, and pytest exits 2.

#### The interception window is import time only

This is the constraint that decides the severity, and the original write-up omitted it.

The patch is installed in `pytest_load_initial_conftests` and removed after `pytest_collection`. So
`cache_user_function` can only ever observe callables that are constructed while conftest and test
modules are being imported. Anything built inside a fixture or a test body is created after the
restore and is not intercepted at all. Verified:

```python
def test_runtime_lru_cache_is_not_intercepted():
    ns = {}
    exec("def late(x):\n    return x\n", ns)
    f = functools.lru_cache(maxsize=None)(ns['late'])   # __module__ is None
    assert f(1) == 1
```

```text
1 passed   EXIT=0
```

That removes every runtime-constructed scenario: mocks, `partial` objects built in fixtures, anything
from a test body. To reach this code the offending callable must be created at module scope, during
import, in a module pytest collects.

#### What can and cannot reach it

`@lru_cache` as decorator syntax applies only to a `def` or a `class`; `@` on anything else is a
`SyntaxError`. The exotic callables therefore require the call form `lru_cache(maxsize=None)(obj)`.

| Input | Reachable via `@` | Result |
| --- | --- | --- |
| `__module__` is `None` | yes, inside code `exec`'d with globals lacking `__name__` | crash, exit 2 |
| `__module__` absent (`str.upper`, `dict.get`, `(1).__add__`) | no, call form only | crash, exit 2 |
| `functools.partial`, callable class instance | no, call form only | silent wrong match, no error |

`None` also propagates outward through `functools.wraps`, which copies `__module__`, so a user could
in principle inherit it from a library decorator without writing `exec` themselves.

#### No known trigger

Searched stdlib for a realistic producer of `__module__ is None`:

| Source | `__module__` |
| --- | --- |
| `namedtuple.__new__` | `'namedtuple_P'` |
| `dataclass.__init__` | `'__main__'` |
| `typing.NamedTuple.__new__` | `'namedtuple_NT'` |
| `MagicMock()` | `'unittest.mock'` |
| `mock.create_autospec(fn)` | `None` |

`create_autospec` is the only stdlib producer found, and it is unreachable here: autospecs are built
inside tests and fixtures, after the restore, and nobody caches one with `lru_cache` anyway.

No library sighting and no plausible user story were found. The remaining path requires `exec` with
bare globals, at module import time, in a project that has also configured `lru_cache_disabled`.

Users who hit this adhoc can disable the plugin: `pytest -p no:antilru`, verified to run the crashing
repro clean at exit 0.

#### Triage: Low, no known trigger. Do not schedule.

Downgraded from High through Medium to Low. Finding 3 rewrites `main.py:16` anyway, so fold
`module = getattr(user_function, '__module__', None) or ''` into that change and match against it. If
finding 3 is declined too, drop this finding entirely.

One decision the `or ''` hides: an unattributable function then matches no prefix and is never busted.
That is fail-closed, consistent with allowlist semantics, but it should be deliberate.

The `partial` and callable-instance mis-attribution is a separate claim with the same import-time gate
and no sighting either. It belongs with finding 3, because it is the same question: the allowlist
matches the wrong thing.

### 3. Medium (was High): allowlist matches raw string prefixes, not module-path prefixes

Anchor: `pytest_antilru/main.py:16`.

`startswith` is a plain string comparison, so `app.util` also matches `app.utilities`, `app.utils`,
and `app.utilization`. Users get cache busting in modules they did not list, which looks like the
plugin ignoring their config.

Repro:

```ini
# pytest.ini
[pytest]
lru_cache_disabled =
    app.util
```

```python
# app/utilities.py
from functools import lru_cache

count = 0


@lru_cache
def val():
    global count
    count += 1
    return count
```

```python
# test_prefix.py
from app import utilities


def test_a():
    assert utilities.val() == 1


def test_b():
    # app.utilities is not in the allowlist, only app.util is, so the cache should survive
    assert utilities.val() == 1, 'cache was wrongly busted: prefix over-match'
```

`test_b` fails with `assert 2 == 1`.

Direction: `module == prefix or module.startswith(prefix + '.')`.

#### Provenance: the matching rule was never specified

Issue #27 is sometimes cited as the origin of this feature. It is not. That issue is about hook
timing, asking for the patch to move from `pytest_collection` to `pytest_load_initial_conftests` so
that `AppConfig.ready` imports are intercepted under pytest-django. Neither the issue body nor its two
comments mention allowlists or module matching.

The allowlist arrived unsolicited in PR #35, which closed #27 by doing both things at once. Its
description offers "an option to `lru_cache_disabled` that allows you to specify a list of modules
that lru_cache is disabled for", and asks "Not sure what your thoughts are on the option or how it
should be implemented." The reply approved the concept, not the mechanics. Across both threads nobody
ever states exact-match against prefix-match, so `startswith` is an unreviewed implementation detail
rather than a deliberate design.

PR #35's own motivating case argues for containment. The author wanted his django app busted while
`django.contrib.auth.password_validation` stayed cached. A user with a package of fifty modules will
write the package name once, not fifty lines, so entries have to cover submodules. Exact-only matching
would not serve the feature; boundary matching does.

#### The repository's own fixture is misconfigured

`tests/pytest_lru_cache_allowlist.ini` lists `tests.main`, which names nothing. There is no
`tests/main/` package and no `tests/main.py`, only `tests/main_test.py`. The commit that added the
file (`6f6493e`) calls the config "functionally equivalent" to the default run, which is only true if
it matches `tests.main_test`. It currently does so through the raw-prefix bug. The correct value is
`tests.main_test`.

This is the only known instance of anything depending on the loose match, and it is an accident rather
than an intentional use of the behavior.

#### Triage: Medium, patch release

Downgraded from High. The line is unreachable unless `lru_cache_disabled` is non-empty, because an
empty allowlist takes the `else` branch at `main.py:19-20`. It further needs a naming collision
between a listed entry and a sibling module. Impact is confined to tests.

The fix ships as a patch. The raw-prefix behavior was never documented; `README.md` documents
containment, so the change moves the code onto its published contract. Release 2.0.1 set the
precedent, shipping "`lru_cache_disabled` now applies to `@lru_cache` (no parentheses) form" as a
patch, which likewise altered which modules get busted under an unchanged config.

A regex implementation was considered and rejected. Allowlist entries are configuration strings, not
patterns, so an unescaped `re` turns user dots into wildcards and creates a new over-match
(`re.match('app.util(\.|$)', 'appXutil')` succeeds). With `re.escape` it does what two string
comparisons already do, at the cost of an import and worse readability.

#### Known limitation, deliberately not fixed

`functools.partial` instances resolve `__module__` through their class, so every partial reports
`'functools'` regardless of where it was constructed. With an allowlist set, `lru_cache(partial(...))`
written inside a listed module is never matched and its cache is never cleared. This is the opposite
error from the prefix over-match, and there is no fix: nothing on a partial records its construction
site, and `p.func.__module__` fails on the common case of wrapping a stdlib callable. Wrapping a
partial in `lru_cache` is rare enough that this stays recorded rather than coded around, and it is
kept out of `README.md` and `CHANGELOG.md`.

#### Implementation is scoped

The full prompt, including the coupled edits to `tests/pytest_lru_cache_allowlist.ini`, the skip guard
in `tests/allowlist_test.py`, `AGENTS.md`, `README.md`, and `CHANGELOG.md`, is in
`docs/future-work-allowlist-boundary-match.md`. Finding 2's guard is folded into the same change.

### 4. Low (was Medium): caches created after collection are never busted

Anchor: `pytest_antilru/main.py:75`.

Because the patch is removed when collection ends, any `lru_cache` applied later is untracked:
lazy imports inside a test body, modules imported by a fixture, decorators applied at runtime. No
warning is emitted and `README.md` does not mention the limitation, so the plugin's core promise fails
quietly for those cases.

Repro:

```python
# lazy.py
from functools import lru_cache

n = 0


@lru_cache
def val():
    global n
    n += 1
    return n
```

```python
# test_lazy.py
def test_a():
    import lazy
    assert lazy.val() == 1


def test_b():
    import lazy
    assert lazy.val() == 1, 'lazily imported module cache not busted'
```

Both tests pass, which proves the cache was *not* busted between them.

#### How caches come to be created after collection

There are two mechanisms, and everything else is an instance of one of them.

The first is a module-level `@lru_cache` in a module whose first import happens after collection.
Collection imports test modules and, transitively, whatever they import at the top level. A module
reached only by a function-body import is first imported when that function runs, which is during a
test. Function-body imports are typically a circular-import workaround or a deferred optional
dependency.

The second is `functools.lru_cache` called as a function at runtime rather than applied as a
decorator at import time, for example `self._lookup = functools.lru_cache(self._lookup_uncached)` in
a constructor. This has nothing to do with import placement, so the interception window never covers
it.

Verified in one run: a module imported at collection had its cache cleared between tests, while a
module imported inside a test body, a module imported by a fixture, and a runtime
`functools.lru_cache(...)` call all kept their values.

Instrumenting `functools.lru_cache` to log every call after collection ends, then running this
repository's own suite, produced one call, from `tests/main_test.py:76`, which does it deliberately.
That is a minimal environment with no application code, so it bounds nothing about real projects, but
it does show the concern that widening would sweep up large numbers of stdlib and third-party caches
is unfounded.

#### Triage: documented, not fixed

The plugin's scope is clearing application-code caches between tests to prevent pollution. Modules
that are only imported at runtime fall outside that scope by decision: PEP 8 asks for imports at the
top of the module, function-body imports are a workaround, and accommodating them is not this
plugin's job.

The gap is now documented rather than fixed. `README.md` gained a "What gets busted" section stating
the covered case and the two uncovered ones, and `docs/architecture.md` explains the interception
window, the reasons for both hook choices, and the name-binding behavior below.

Severity drops from Medium to Low. Nothing is silent any more, and the uncovered cases are stated
where a user looks first.

#### Unresolved sub-issue: recording depends on import style

Removing the patch rebinds the attribute `functools.lru_cache`. It cannot reach a name bound to the
wrapper object elsewhere. A module that ran `from functools import lru_cache` during collection keeps
its own reference to the wrapper, so its runtime `lru_cache(...)` calls still record. A module that
ran `import functools` does a fresh attribute lookup, gets the restored original, and does not
record.

Verified: two modules differing only in import style, both creating a cache at runtime during the
same test, gave `from_import currsize: 0` (cleared) and `attr_access currsize: 1` (not cleared).

So the predicate is not "was the cache created before the restore" but "did this call site's name
resolution reach the wrapper object". Two otherwise identical modules behave differently based on a
stylistic choice, and unlike the cases above this lands on code that follows PEP 8.

This also means the restore is incomplete in a way finding 1 does not capture: the wrapper survives
in the globals of every module that imported it by name, for the life of the process.

A small fix exists and is not scheduled. A module-level `collection_complete` flag, set beside the
restore in `pytest_collection` and reset in `pytest_load_initial_conftests`, with an early return in
`cache_user_function`. That makes the documented rule true rather than approximately true, and it is
independent of findings 1, 5, and 6. It narrows behavior, removing recording that currently works by
accident, so it would be a minor release rather than a patch.

No decision has been taken on it.

### 5. Medium: one failing `cache_clear` aborts the rest of the teardown loop

Anchor: `pytest_antilru/main.py:88-89`.

The loop has no error handling. The first exception stops it, so every cache after the failing entry
stays populated, and the same exception repeats on every later teardown.

Repro:

```python
# test_raise.py
from functools import lru_cache

from pytest_antilru import main


@lru_cache
def good():
    return object()


class Bomb:
    __module__ = 'test_raise'

    def cache_clear(self):
        raise RuntimeError('bad cache_clear')


def test_a():
    good()
    main.CACHED_FUNCTIONS.insert(0, Bomb())


def test_b():
    assert good.cache_info().currsize == 0, 'later caches not cleared after an exception'
```

Result: `test_b` fails, and both tests report

```text
PluggyTeardownRaisedWarning: A plugin raised an exception during an old-style hookwrapper teardown.
RuntimeError: bad cache_clear
```

The trigger above is synthetic. The point is the missing guard, not the `Bomb` class. Direction: wrap
each `cache_clear()` call, keep going, and surface the failures once at the end of the loop.

### 6. Medium: `CACHED_FUNCTIONS` is an append-only list of strong references

Anchors: `pytest_antilru/main.py:9`, `:17`, `:20`.

Every wrapper ever created during collection is pinned for the life of the process, and teardown cost
is linear in that list for every single test. Nothing is ever removed, and the list is not reset
between in-process sessions, so wrappers from a previous session keep being cleared.

Evidence from a trivial run in this repository: 16 entries recorded, of which 8 were
`FoldedCase.lower` from `importlib.metadata`. A library that applies `lru_cache` inside a loop or a
factory adds one entry per call, so the list grows with no bound during collection.

Repro:

```python
# test_count.py
from pytest_antilru import main


def test_count():
    fns = main.CACHED_FUNCTIONS
    print('tracked count:', len(fns))
    print('sample:', [getattr(f, '__wrapped__', f).__qualname__ for f in fns][:15])
```

Run with `pytest -s test_count.py`.

Direction: hold weak references, and clear the collection at unconfigure time.

### 7. Low: unknown kwargs are warned about, then silently discarded

Anchors: `pytest_antilru/main.py:37-38`, `:48`.

Line 48 reassigns `kwargs = {}`, so anything the user passed beyond `maxsize` and `typed` is dropped
and the call degrades to plain defaults instead of raising the `TypeError` real `lru_cache` would
raise. The warning goes to the root logger via `logging.warning`, so it does not appear in pytest's
warnings summary and cannot be filtered with `-W`.

Direction: use `warnings.warn` so pytest surfaces it, and forward the unknown kwargs to the real
`lru_cache` so its own error surfaces instead of being masked.

### 8. Low: `addini` is called from `pytest_load_initial_conftests`

Anchor: `pytest_antilru/main.py:26`.

Registration belongs in `pytest_addoption`. As written, the option is registered late, and a
`ValueError` results if any other conftest or plugin registers the same `lru_cache_disabled` name.

## Suggested sequencing

1. Finding 1 is triaged as deferred. It is dormant until the test suite runs two pytest sessions in
   one interpreter, and the fix is scoped in `docs/future-work-pytester-migration.md`.
2. Finding 2 is triaged as Low with no known trigger and is not scheduled on its own. Its one-line
   guard rides along with finding 3, which rewrites the same line. Finding 5 is a pure bug fix with no
   user-visible behavior change and can land with a regression test.
3. Finding 3 is triaged as Medium and scoped in `docs/future-work-allowlist-boundary-match.md`, which
   covers the coupled edits to the repository's own allowlist fixtures and documentation. It ships as
   a patch release.
4. Finding 4 is triaged as documented rather than fixed. The restore stays at the end of collection,
   and the uncovered cases are stated in `README.md` and `docs/architecture.md`. Finding 1's fix
   leaves the `pytest_collection` restore in place, so the two do not interact. The import-style
   sub-issue recorded under finding 4 is still open.
5. Findings 6, 7, and 8 are independent cleanups.

Note for any fix to finding 1 or 4: `tox.ini` runs the same test pair forward and in reverse, and
`tests/teardown_order_test.py` plus the hookwrapper probe in `tests/conftest.py` lock in the teardown
ordering invariant. Re-run the full `tox` matrix, not just `pytest`, since coverage is gated at 100
percent for both the package and the tests.
